# 工程表盘、测试分类与限定修改

工作台以 RTL 为主区域：左侧工程与源文件，中间带行号的代码，右侧关联工程证据。测试和会话是独立工作视图，修改范围与差异按需展开。模型 API 仍停用，浏览页面不会启动 EDA；检索、报告读取和手动编辑可在本机使用。

## 工程资产

从“工程资产”选项目，查看 RTL、模块声明、测试台、约束与依赖。功能、综合、setup、hold、约束、布线、DRC、CDC、形式验证与板卡证据分别显示。源码存在表示有实现；没有绑定证据的领域显示未验证。旧报告保留当时结论与当前输入匹配状态，聚合成绩不会分摊成每个模块通过。

目录只读取批准的 `projects` 和 `examples/digital`、`examples/analog`；外部依赖由工程清单显式列出。模块名通过词法扫描得到，不推断宏展开、层次或正确性。忽略生成目录、隐藏配置及二进制产物。列表最多 80 个项目，每个项目最多 400 个文件，文件最大 1 MiB；被截断的清单禁止创建修改候选。

## 限定修改

1. 打开可编辑的 RTL，选择包含端点的行范围并写明目标；一个文件最多一个连续范围，一次最多八个文件。
2. 保存计划，宿主先核对源码预览的 SHA-256，拒绝旧行号对应新内容，再冻结清单内的源码、测试与约束哈希及原件快照。会话可关联该计划。
3. 编辑选中范围的替换内容，查看前后差异。范围外文件、测试台、约束和依赖不能通过此接口修改。
4. 确认“生成修改候选”。宿主重新检查输入与预览指纹，只在独立目录写入候选；重复提交被拒绝。
5. 核对候选完整性。原件变化、快照损坏、候选被改或出现未审阅文件都会明确报错。

计划存在 `.eda-state/workbench-changes/<id>/`，候选在 `artifacts/scoped-change-<id>/candidate/`，清单在同层 `candidate-manifest.json`。没有直接覆盖原工程的接口。外部依赖被保留到 `@dependencies`，不会自动重写构建脚本。

候选是已枚举源码的变更交付，不是独立可构建工程。生成候选只证明变更范围与文件完整性，功能、时序、CDC/DRC 等仍为 `not_run`。工程验证需要显式声明固定 checker、约束、依赖与候选输入的 workflow。当前修改入口接受手动替换内容，不调用模型生成补丁；此处的范围控制不宣称约束任意 Pi shell 或外部工具。

## 测试分类

| 层 | 逐条单位 | 可见细分与证据 |
|---|---|---|
| 软件机制 | Node 测试 | 会话、工作流、范围控制、知识契约、工具、trace、优化等；Python 只有汇总时保留原汇总 |
| RAG 与 SOP | 查询 | 可见检索问题与无关查询；显示题集/知识版本，不能等同回答正确率 |
| 工具与案例 | benchmark 变体 | 类别、家族、难度、种子、负对照、最新结果及历史；定义了案例不代表已执行 |
| 工程验收 | 工程 × 领域 | 每个领域独立证据，未要求/未运行、失败与待审查保留 |
| Agent 在线任务 | 会话任务 | 只认真实 Agent 评测回执；假 SDK、界面交互不算真实任务分数 |

不同层不合并总通过率。页面保留失败、未运行、预期失败/超时，以及当前定义是否匹配；历史运行不会在浏览时重新执行。扫描数量有上限，显示的是保留回执的可观察投影，不是无限历史数据库。

## 实现与复用

入口为 `src/workbench.mjs`，项目投影在 `src/workbench-projects.mjs`，测试投影在 `src/workbench-testing.mjs`，限定修改在 `src/workbench-changes.mjs`。它们沿用现有会话归属、同源访问、持久化和工程证据合同。

成熟项目的可借鉴机制、官方出处与许可证见 [复用调研](workbench-reuse-v08.md)。验收继续使用 `npm run validate:agent`，包含项目路径、错误版本、缺失证据、限定范围与候选完整性的反例。当前发布结果见 [发布回执](../release/README.md)。

原有入口：[会话验收](workbench-v07-acceptance.md) · [评测协议](evaluation.md) · [工作流合同](agent-workflow-and-trace-contract.md) · [协作与 trace](agent-framework-and-traces.md)。
